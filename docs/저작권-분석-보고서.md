# 뮤스(Mews) 뉴스 수집 구조의 저작권 분석 및 개선 제안 보고서

> 작성일: 2026-06-19
> 대상: 뮤스(Mews) — 뮤지컬 뉴스 검색 웹앱
> 목적: 현재 기사 수집(크롤링) 구조에 대한 한국법 기반 저작권 위험 분석과, 합법적 범위 내에서 기사 정보를 더 풍부하게 제공하기 위한 개선 방안 검토
>
> ⚠️ **면책 고지**: 본 문서는 코드 구조에 대한 기술적·법리적 검토 의견이며, 변호사의 공식 법률자문이 아닙니다. 실제 서비스 확장·수익화 전에는 저작권 전문 변호사의 자문을 받으시길 권장합니다.

## 1. 현재 수집 구조 요약 (기술 분석)

뮤스는 백엔드 서버 없이 **Netlify Functions 2개**로 동작하며, 데이터 흐름은 다음과 같습니다.

### 1-1. `netlify/functions/news.js` — 뉴스 목록 수집

- **대상**: `https://news.google.com/rss/search` (구글 뉴스 RSS)
- **방식**: 검색어에 `when:1y`, `when:1m` 시간대 변형을 붙여 RSS 피드를 병렬 수집 → 중복 제거
- **추출 항목**: `title`(제목), `link`(구글 뉴스 리다이렉트 링크), `pubDate`(발행일), `source`(언론사명)
- **반환**: 위 4개 필드만 JSON 배열로 클라이언트에 전달
- 봇 차단 회피용으로 **브라우저 User-Agent(Chrome)** 를 위장하여 요청

### 1-2. `netlify/functions/summary.js` — 기사 요약(리드) 추출

이 부분이 **저작권상 가장 민감한 핵심**입니다. 동작 단계:

1. 구글 뉴스의 암호화된 리다이렉트 링크를, 구글 내부 비공개 엔드포인트인 **`batchexecute`(`Fbv4je`)를 리버스 엔지니어링**하여 원문 URL로 해석
2. 해석된 **언론사 원문 페이지에 직접 접속**(브라우저 UA 위장, 문자셋 자동 감지)
3. 원문 HTML에서 다음을 **추출하여 반환**:
   - 1순위: `og:description` / `meta[name=description]` / `twitter:description` 메타 태그
   - 2순위: 메타가 없으면 **본문 첫 문단(`<p>`) 중 60자 이상인 것**
4. 클라이언트(`app.js`)는 이 텍스트를 카드 본문에 **최대 약 180자**로 잘라 표시 (`finalize()` → 177자 + `…`)

### 1-3. 클라이언트 표시 (`app.js`)

- 카드: 언론사명 + 제목 + 요약(180자) + 날짜
- 카드 전체가 원문(`target="_blank"`)으로 가는 **링크**
- 제목은 끝의 `" - 언론사명"` 제거 가공, 날짜는 `YYYY년 MM월 DD일` 변환

## 2. 저작권법 쟁점별 분석

### 2-1. 기사 제목(제호)의 저작물성 — 위험 낮음

- 대법원은 일관되게 **저작물의 제호(제목) 자체는 저작권 보호 대상이 아니다**라고 봅니다(짧은 어구는 사상·감정의 창작적 표현으로 보기 어려움).
- 따라서 `news.js`가 **제목을 수집·표시하는 것 자체의 저작권 침해 위험은 낮습니다.**
- 다만 **제목을 대량으로 체계적으로 수집·재배열**하면 저작권이 아니라 **부정경쟁방지법 / 데이터베이스권** 쟁점으로 옮겨갈 수 있습니다(§2-5, §3 참조).

### 2-2. "사실의 전달에 불과한 시사보도"(저작권법 제7조 제5호) — 한정적 면책

- 저작권법 제7조 제5호는 **"사실의 전달에 불과한 시사보도"** 를 보호받지 못하는 저작물로 규정합니다.
- 그러나 판례(대법원 2006도2074 등)는 이 면책을 **매우 좁게** 해석합니다. 인사·부고·간단한 사건사고처럼 **"누가 써도 같은" 정형적·간결한 사실 나열**만 해당하고, **기자의 취재·선택·구성·문장 표현이 들어간 일반 기사는 저작물로 보호**됩니다.
- 뮤지컬 관련 기사(공연 리뷰, 인터뷰, 기획기사, 캐스팅 분석 등)는 **대부분 창작적 표현이 있는 보호 대상 저작물**입니다. 따라서 "시사보도라서 괜찮다"는 논리는 **이 서비스에 거의 적용되지 않습니다.**

### 2-3. 리드/첫 문단 추출 — **가장 큰 위험 지점 (복제·전송권)**

`summary.js`의 핵심 동작인 **본문 첫 문단(`<p>`) 추출**은 다음 점에서 위험합니다.

- 기사의 **리드 문장(첫 문단)** 은 기사에서 가장 공들인 핵심 표현으로, **창작적 표현일 가능성이 높습니다.**
- 이를 서버가 가져와 클라이언트로 보내 화면에 보여주는 것은 저작권법상 **복제권(제16조)·공중송신(전송)권(제18조)** 에 저촉될 수 있습니다.
- **og:description 메타 태그**도 안전지대가 아닙니다. 상당수 언론사가 og:description에 **리드 문장을 그대로** 넣기 때문에, 결과적으로 보호 대상 표현을 복제·전송하는 셈이 될 수 있습니다.
- 길이를 180자로 자른다고 해서 자동으로 면책되지 않습니다. **분량보다 "창작적 표현의 핵심을 가져왔는지(질적 판단)"** 가 중요합니다.

> **결론**: `summary.js`의 본문 문단 추출은 **현재 구조에서 저작권 침해 소지가 가장 큰 부분**입니다.

### 2-4. 인용(제28조)·공정이용(제35조의5) — 부분적 방어 가능하나 한계

- **제28조(공표저작물의 인용)**: "보도·비평·교육·연구 등을 위하여 **정당한 범위 안에서 공정한 관행에 합치되게**" 인용하면 적법.
  - 유리한 점: 출처(언론사)를 명시하고, 원문 링크를 제공하며, 짧은 발췌만 보여준다는 점.
  - 불리한 점: 본 서비스의 인용은 **"비평·보도·연구"라는 인용 목적이 약하고**, 단순히 **원문의 핵심 내용을 대체 전달**하는 성격이 강합니다. 또한 **인용은 "주(主)인 자기 저작물 + 종(從)인 인용"** 구조여야 하는데, 카드에는 자체 창작 콘텐츠가 거의 없어 **"주-종 관계"가 성립하기 어렵습니다.**
- **제35조의5(공정이용)**: 4요소(이용 목적·성격, 저작물 종류, 이용된 부분의 양과 질, 시장에 미치는 영향)를 종합 판단.
  - 가장 불리한 요소는 **"잠재적 시장에 미치는 영향"** 입니다. 이용자가 카드 요약만 보고 원문에 가지 않으면 언론사의 트래픽·광고 수익을 잠식한다고 평가될 수 있습니다.
  - 다만 현재 뮤스는 **요약이 짧고 원문 링크로 클릭을 유도**하므로, 비영리·소규모·검색 보조 성격이 인정되면 공정이용 항변 여지는 일부 있습니다.

> **요지**: 인용·공정이용 항변은 **"짧게 + 출처 명시 + 원문 링크 + 비영리"** 일 때 가장 강하고, **"길게 + 원문 대체 + 수익화"** 로 갈수록 급격히 약해집니다. 개선 방향(섹션 5)도 이 기준선을 넘지 않는 것이 핵심입니다.

### 2-5. 데이터베이스제작자의 권리(제93조) & 링크 적법성

- **링크 자체는 적법**: 대법원은 **단순 링크(원문으로 이동시키는 링크)는 복제·전송에 해당하지 않아 저작권 침해가 아니다**라고 봅니다. 뮤스가 카드 클릭 시 원문으로 보내는 구조는 **이 점에서 안전**합니다.
- **구글 뉴스 데이터베이스**: 구글 뉴스 RSS를 대량 수집하는 것은 구글의 **데이터베이스권/이용약관** 쟁점을 일으킬 수 있습니다(§3-2).

## 3. 저작권법 외 추가 법적 쟁점

### 3-1. 부정경쟁방지법 — 성과 도용(제2조 제1호 파목) & 데이터 부정사용(카목)

저작권 침해가 아니더라도 **부정경쟁방지법**에 걸릴 수 있습니다. 이는 크롤링 분쟁의 실제 핵심 쟁점입니다.

- **파목(성과 도용)**: "타인의 **상당한 투자·노력으로 만든 성과** 등을, 공정한 상거래 관행·경쟁질서에 반하는 방법으로 **무단 사용**하여 경제적 이익을 침해"하는 행위.
- **카목(데이터 부정사용, 2021년 신설·2022.4.20 시행)**: 거래 목적으로 제공되는 데이터를 부정하게 취득·사용하는 행위.
- **야놀자 v. 여기어때 사건**의 시사점:
  - **형사(대법원 2021도1533, 2022.5.12)**: 공개된 정보이고 서버 장애를 일으킬 정도가 아니라는 등 이유로 **정보통신망법·저작권법 위반 무죄**.
  - **민사**: 그러나 별도로 **상당한 투자로 구축한 DB를 무단 이용한 점**을 들어 **부정경쟁행위 성립 → 손해배상 인정**.
  - 교훈: **"형사 무죄 ≠ 민사 적법"**. 크롤링이 형사처벌을 피하더라도 **민사상 부정경쟁행위로 손해배상** 책임이 생길 수 있습니다.
- 뮤스에 대한 적용: 현재는 **비영리·소규모**라 분쟁 가능성이 실무상 낮지만, **수익화하거나 트래픽이 커지면** 언론사·구글 측이 파목/카목을 근거로 문제 삼을 여지가 생깁니다.

### 3-2. 구글 이용약관 위반 & 비공개 API 리버스 엔지니어링

- `summary.js`가 사용하는 **`batchexecute`(`Fbv4je`) 엔드포인트는 구글의 공개 API가 아니라 내부 통신을 리버스 엔지니어링**한 것입니다.
  - 이는 **구글 서비스 약관 위반** 소지가 크며(자동화 접근·우회 금지 조항), 약관 변경 시 **언제든 동작이 깨질 수 있는 기술적 불안정성**도 동반합니다.
  - 브라우저 **User-Agent 위장**도 약관·접근정책 우회로 해석될 수 있습니다.
- 법적 리스크는 저작권보다 **계약(약관) 위반 / 부정경쟁** 영역에 가깝습니다.

### 3-3. robots.txt & 언론사 개별 이용약관

- `summary.js`는 언론사 원문 페이지에 **직접 접속하여 본문을 긁어옵니다.** 많은 언론사가 이용약관에서 **무단 복제·크롤링을 금지**하고 있고, robots.txt로 봇 접근을 제한하기도 합니다.
- 현재 코드는 **robots.txt를 확인하지 않습니다.** 이는 "공정한 관행" 위반 정황으로 불리하게 작용할 수 있습니다.

### 3-4. 한국언론진흥재단 뉴스저작권 신탁

- 다수 국내 언론사는 기사 저작권을 **한국언론진흥재단**에 신탁하고, **뉴스저작권 유통 플랫폼(NewsStore 등)** 을 통해 유료 라이선스로 제공합니다.
- 즉, 기사 본문·리드의 **합법적 이용 경로(유료 라이선스)가 실제로 존재**합니다. 이는 "공정이용으로 무단 사용"이 더 불리해지는 요소이자, **합법적 대안이 마련되어 있다**는 의미이기도 합니다(섹션 5).

## 4. 위험도 종합 평가

| 구성 요소 | 행위 | 주요 법적 근거 | 위험도 |
|---|---|---|---|
| 제목 수집·표시 | 제호 표시 | 저작권법(제호 비보호) | 🟢 낮음 |
| 언론사명·발행일·링크 | 사실정보 표시 | 사실정보, 단순링크 적법 | 🟢 낮음 |
| 원문으로의 링크 이동 | 단순 링크 | 대법원 단순링크 비침해 | 🟢 낮음 |
| **본문 첫 문단 추출·전송** | 복제·전송 | **복제권·전송권(제16·18조)** | 🔴 **높음** |
| og:description 추출·전송 | 복제·전송 | 리드 포함 시 복제·전송권 | 🟠 중간 |
| 구글 RSS 대량 수집 | 자동 수집 | 구글 약관·DB권 | 🟠 중간 |
| **batchexecute 리버스 엔지니어링** | 비공개 API 우회 | **구글 약관·부정경쟁** | 🟠 중간(기술 불안정 동반) |
| UA 위장 / robots 미확인 | 접근정책 우회 | 공정관행 위반 정황 | 🟠 중간 |
| 향후 수익화 시 전체 | 성과 무단사용 | **부정경쟁방지법 파/카목** | 🟠 영리화 시 상승 |

**총평**: 현재 뮤스는 **비영리·소규모**라 즉각적 분쟁 가능성은 낮지만, 구조 자체에는 **(1) 기사 본문 추출(복제·전송권)**, **(2) 구글 비공개 API 우회** 라는 두 개의 명확한 약한 고리가 있습니다. 특히 사용자가 요청한 **"앱 내에서 기사 내용을 더 많이 보여주는 방향"** 은, 아무 조치 없이 진행하면 **🔴 위험 영역을 정면으로 키우는** 결과가 됩니다. 따라서 확장은 반드시 **합법적 데이터 출처 + 인용 한계 준수** 위에서 설계해야 합니다.

## 5. 법을 위반하지 않으면서 정보를 더 제공하는 방안 (검토용 제안)

> 아래는 **즉시 구현이 아니라 검토용 옵션**입니다. "앱 내에서 기사 내용을 더 보고 싶다"는 목표를 **위험을 낮추는 순서**로 정리했습니다.

### 방안 A. 공식 뉴스 API로 출처 전환 — **가장 권장**

비공개 크롤링을 **정식 라이선스가 있는 공식 채널**로 바꾸는 것이 근본 해법입니다.

| 출처 | 제공 내용 | 장점 | 유의점 |
|---|---|---|---|
| **빅카인즈(BigKinds) Open API** (한국언론진흥재단) | 기사 메타데이터, **본문 앞 200자**, 키워드/분석 | 국내 다수 언론사 **합법 제공**, 공적 신뢰 | 본문 전문은 유료(NewsStore), API 신청·약관 준수 필요 |
| **네이버 검색 API(뉴스)** | 제목·요약·링크·발행일 | 안정적·문서화됨, 무료 쿼터 | 표시 가이드·출처 표기 약관 준수, 본문 전문 미제공 |
| **언론사 공식 RSS** | 제목·요약·링크 | 언론사가 **스스로 공개·배포 의도** | 언론사별 약관 상이, 요약 길이 제각각 |

- **권장 조합**: 목록/검색은 **네이버 뉴스 검색 API** 또는 **공식 RSS**, "본문을 더 보여주는 기능"은 **빅카인즈 API의 합법 제공 범위(앞 200자 등)** 활용.
- 효과: `batchexecute` 리버스 엔지니어링과 언론사 직접 크롤링을 **제거**할 수 있어 🔴/🟠 위험을 동시에 낮춤.

### 방안 B. "더 보기"는 본문 복제가 아니라 **원문으로 보내기** 강화

- 앱 내에서 **본문 전문을 표시하는 대신**, "원문에서 이어 읽기" UX를 고도화(미리보기 카드, 원문 매체 로고, 예상 읽기 시간 등).
- 이는 **단순 링크(적법)** 범위를 유지하면서 사용자 경험만 끌어올리는 안전한 방향입니다.
- 인앱 브라우저/iframe로 **원문을 그대로 임베드**하는 것은 매체 약관·프레이밍 이슈가 있으니, **새 탭 이동**을 기본으로 권장.

### 방안 C. 인용 한계를 지킨 "짧은 발췌 + 명확한 출처" 표준화

본문 일부를 계속 보여주려면, **인용(제28조)·공정이용 항변이 가장 강한 형태**로 규격화합니다.

- ✅ 발췌는 **짧게**(현재 180자 수준 이하 유지, 늘리지 않기)
- ✅ **출처(언론사) + 발행일 + 원문 링크** 항상 병기 (이미 잘 되어 있음 — 유지·강화)
- ✅ `summary.js`의 **"본문 첫 문단 직접 추출(2순위 로직)"은 제거**하고, 매체가 **배포 목적으로 스스로 공개한 og:description/RSS description**만 사용 → "매체가 공개 의도로 내놓은 요약"이라 방어가 더 쉬움
- ✅ **robots.txt 존중** 로직 추가, **UA 위장 대신 식별 가능한 User-Agent + 연락처** 명시(예: `MewsBot/1.0 (+연락처)`) → "공정한 관행" 정황 강화
- ✅ 캐시·요청 빈도 제한(rate limit)으로 상대 서버 부하 최소화

### 방안 D. **자체 생성 콘텐츠**로 "주-종 관계" 만들기

- 카드에 **뮤스가 직접 만든 부가정보**(작품 개요, 공연장·기간, 캐스팅, 관련 작품 추천, 사용자 코멘트 등)를 더해, 인용이 **"종(從)"** 이 되는 **"주-종 관계"** 를 형성하면 인용 항변이 강해집니다.
- 또는 **여러 기사를 종합한 자체 요약/큐레이션**을 사람이 작성. 단, **AI로 원문을 자동 요약**하는 것은 원문 표현에 의존하면 **2차적저작물/복제** 논란이 생길 수 있으니, "사실 위주로 재서술 + 출처 명시"가 안전.

### 방안 E. 제휴·라이선스 (중장기, 수익화 시 필수)

- 트래픽이 커지거나 수익화한다면, **한국언론진흥재단/언론사와의 정식 콘텐츠 제휴(유료 라이선스)** 가 가장 확실한 합법화 경로입니다.
- 비영리·교육 목적이라면 **공공데이터포털의 뉴스 메타데이터 데이터셋** 활용도 검토 가치가 있습니다.

## 6. 권고 요약

1. **단기(위험 제거)**: `summary.js`의 **본문 첫 문단 직접 추출 로직 제거**, og:description/RSS description만 사용, robots.txt 존중·UA 정직화. → 🔴 위험을 🟠 이하로 낮춤.
2. **중기(출처 전환)**: 구글 비공개 `batchexecute` 의존을 걷어내고 **네이버 검색 API / 빅카인즈 API / 공식 RSS** 로 이전. → 구조적 합법성 확보 + 기술 안정성 향상.
3. **기능 확장(목표 달성)**: "본문을 더 보여주는" 방향은 **본문 복제 확대가 아니라**, ⓐ 빅카인즈 합법 제공 범위(앞 200자) + ⓑ 자체 부가정보(주-종 관계) + ⓒ 원문 이어읽기 UX 강화로 구현.
4. **수익화 전제 시**: 반드시 **정식 라이선스/제휴** 확보 및 변호사 자문.

핵심 원칙 한 줄: **"매체가 스스로 공개·배포한 것만, 짧게, 출처와 원문 링크를 붙여, 자체 콘텐츠와 함께"** — 이 선을 지키면 더 풍부한 기능으로 확장하면서도 위험을 통제할 수 있습니다.
